# /he:judge - 판별자 (Discriminator)

> 하네스 엔지니어링 3단계: 생성자가 작성한 반영 계획서를 검증하고, 누락/오류를 탐지합니다.

## Triggers
- `/he:generate` 이후 반영 계획서 검증 요청
- 논문 변경사항의 코드 반영 완전성 확인이 필요할 때
- GAN 루프에서 반복 검증 시

## Context Trigger Pattern
```
/he:judge [--strict] [--focus formula|missing|consistency|all] [--pass-threshold 80]
```

### Options
- `--strict`: 모든 차이점이 100% 반영되어야 통과
- `--focus formula`: 수식 변경 반영에 집중 검증
- `--focus missing`: 빠진 구현 탐지에 집중
- `--focus consistency`: 기존 문서/코드와의 정합성에 집중
- `--pass-threshold`: 통과 기준 점수 (기본 80%)

## Behavioral Flow

### Phase 1: 검증 준비
1. **기획서 로드**: `/he:plan`의 원본 차이점 목록 확인
2. **생성자 결과 로드**: `/he:generate`의 반영 계획서 확인
3. **코드 현황 확인**: 대상 코드 파일의 현재 상태 읽기

### Phase 2: 다면 검증

#### 완전성 (Completeness) — 빠진 것 없는가?
- 기획서의 모든 FORMULA 변경이 반영 계획에 포함되었는가?
- Paper B의 새로운 내용이 "빠진 구현"으로 식별되었는가?
- 기존 planner 이슈(A~G)와의 연결이 빠짐없이 되었는가?
- **독립 검증**: 판별자가 직접 Paper A/B를 재비교하여 생성자가 놓친 차이점 탐색

#### 정확성 (Accuracy) — 맞는가?
- 코드 파일/라인 매핑이 정확한가? (실제 파일 읽어서 확인)
- 수식 변경의 코드 반영 방향이 올바른가?
- 우선순위 배정이 영향도에 부합하는가?

#### 정합성 (Consistency) — 기존 분석과 충돌 없는가?
- `planner/saddlepoint_pag_alignment_plan.md`의 기존 결론과 충돌하는 부분
- `revision/revision1.md`의 기존 수정 방향과 모순되는 부분
- `result/verification_report.md`의 검증 결과와 불일치하는 부분

#### 실행 가능성 (Feasibility) — 실제로 할 수 있는가?
- 제안된 코드 수정이 기존 아키텍처에서 실현 가능한가?
- 의존성 충돌이 없는가?
- 수정 범위가 합리적인가?

### Phase 3: 판정
1. **점수 산출**: 각 관점별 점수 계산
2. **누락 목록 생성**: 생성자가 놓친 항목 구체적으로 나열
3. **통과/반려 결정**: 기준 점수 기반

## Output Format

```markdown
## 판별 결과: 반영 계획서 검증

### 종합 판정: PASS / FAIL / CONDITIONAL_PASS

### 점수표
| 관점 | 점수 | 상태 | 비고 |
|------|------|------|------|
| 완전성 | ?/100 | | 누락 N건 |
| 정확성 | ?/100 | | 오류 N건 |
| 정합성 | ?/100 | | 충돌 N건 |
| 실행가능성 | ?/100 | | |
| **종합** | **?/100** | | |

### 누락된 차이점 (생성자가 놓친 항목)
| # | Paper B 위치 | 내용 | 영향 코드 |
|---|-------------|------|-----------|
| 1 | Section 2.4 | 새 정의 추가 | moments.py |

### 오류 수정 필요
| # | 생성자 항목 | 문제 | 수정 제안 |
|---|-----------|------|-----------|
| 1 | 코드수정 #2 | 잘못된 라인 번호 | L270 → L285 |

### 정합성 충돌
| # | 생성자 제안 | 기존 문서 | 충돌 내용 |
|---|-----------|-----------|-----------|
| 1 | SDC +0.5 반영 | revision1.md 섹션8 | -0.5가 표 재현에 더 적합 |

### 피드백 (생성자 재생성용)
1. **[필수]** 누락 항목 #1~N 반영 필요
2. **[필수]** 오류 항목 #1~N 수정 필요
3. **[권장]** 정합성 충돌 해결 방안 제시
```

## GAN Loop Protocol

- **PASS**: 반영 계획서 확정. 실제 코드 수정 진행 가능.
- **CONDITIONAL_PASS**: 권장 사항만 남음. 사용자 판단 후 진행.
- **FAIL**: 필수 피드백을 생성자에게 전달하여 재생성.

```
FAIL → /he:generate --iterate → /he:judge → ... (최대 3회)
3회 초과 → 사용자 에스컬레이션 (논문 원문 재확인 필요)
```

## Boundaries

**Will:**
- 기획서 원본 diff와 생성자 반영 계획을 교차 검증
- 독립적으로 Paper A/B를 재비교하여 누락 탐지
- 기존 분석 문서(`planner/`, `revision/`, `result/`)와의 정합성 확인
- 코드 파일을 실제로 읽어 매핑 정확성 검증

**Will Not:**
- 코드를 직접 수정하지 않음 (별도 구현 단계)
- 기획서에서 식별하지 않은 범위 외 차이를 요구하지 않음
- 논문의 학술적 가치를 판단하지 않음
